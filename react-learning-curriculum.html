🚀 React Learning Curriculum

For an experienced engineer who is new to React, grounded in how crm-web actually uses it. Concepts run simplest → most complex. Each section links a canonical resource, suggests 2–3 short (~20–30 min) exercises, and points to where & why the pattern appears in this codebase.

Stack you're learning into: React 18.3.1, TypeScript 5, function components only (no classes except error boundaries), Redux Toolkit, TanStack React Query v4, react-hook-form, dnd-kit, Nivo charts, and the in-house @wds design system. React here is embedded inside a Rails + Angular monolith, not a standalone SPA — that shapes the back half of this curriculum.

🧱 1. JSX & Rendering Markup

The syntax that lets you write HTML-like markup in JavaScript, and how React turns it into DOM.

📖 Writing Markup with JSX · JavaScript in JSX

  1. Build a static "profile card" component: avatar, name, title, a few stats. Embed JS expressions with {} for the stats.
  2. Convert a chunk of plain HTML (grab any small Rails partial) into valid JSX — fix class→className, self-closing tags, single root element.
  3. Render a list of 5 hard-coded objects to a <table> using only expressions (no .map yet — just to feel JSX).
In crm-web: app/javascript/components/SidebarBadge.tsx — a small, reusable badge. Why React: the badge owns interactive popover state, so it's worth a component instead of server-rendered Slim.

🧩 2. Components & Props (with TypeScript)

Function components, passing data down via props, and typing those props with a TS interface.

📖 Your First Component · Passing Props · Using TypeScript

  1. Refactor exercise #1's profile card to accept all data via a typed ProfileCardProps interface; render 3 different cards from one component.
  2. Build a <Button variant="primary" | "ghost"> with a union-typed prop and a typed onClick.
  3. Make a <StatList items={Stat[]}> component and let TS catch a deliberately mistyped prop.
In crm-web: every component, e.g. components/SidebarBadge.tsx exports an explicit props interface. Why: in a monolith this size, typed props are the contract that stops prop-shape bugs at compile time rather than in production.

🔀 3. Conditional & List Rendering (and keys)

Rendering UI based on a condition, mapping arrays to elements, and why key matters.

📖 Conditional Rendering · Rendering Lists

  1. Render a to-do list from an array with .map + stable key; show an "empty state" when the list is empty.
  2. Add a "show completed only" toggle that conditionally filters the list (no state library, just an inline filtered array).
  3. Deliberately use array index as key, then reorder items, and observe the reconciliation bug — then fix it with stable IDs.
In crm-web: app/javascript/custom_objects/index/components/KanbanColumn.tsx maps cards into columns. Why keys matter here: the Kanban board reorders cards via drag-and-drop, so stable keys are required for correct reconciliation during moves.

🖱️ 4. Event Handling

Responding to user input with handler functions and the synthetic event system.

📖 Responding to Events

  1. Build a counter with +/− buttons and a reset; log the event object to see React's synthetic events.
  2. Make a search box that calls onChange and renders the current keystrokes (controlled-input preview for §13).
  3. Add keyboard handling: a list where ↑/↓ moves a highlighted row (onKeyDown).
In crm-web: custom_objects/index/components/KanbanColumn.tsx wires drag/drop and click callbacks. Why: interactive features (reordering, selecting, persisting to the server) need handlers that translate user actions into state changes and API calls.

🎚️ 5. State with useState

Giving a component memory; when a value should be state vs. a plain variable.

📖 State: A Component's Memory · State as a Snapshot

  1. Build a toggle/accordion that opens and closes with useState<boolean>.
  2. Make a tabs component: clicking a tab sets the active tab in state and swaps the panel.
  3. Build a "like" button that holds a count and a liked flag; explore why two quick updates may need the setX(prev => ...) form.
In crm-web: components/SidebarBadge.tsx uses useState for popover open/closed. Why local state: only this component cares about its popover, so it stays out of Redux — keep state as local as the thing that uses it.

🧠 6. Thinking in React & Derived State

Where state should live, lifting state up, and computing values during render instead of storing duplicates.

📖 Thinking in React · Sharing State Between Components

  1. Build a filterable product table (search + "in stock only") — store only the raw list + filter inputs; compute the filtered list inline.
  2. Take two sibling components (a list and a detail pane) and lift the "selected id" up to their parent.
  3. Find a place where you're tempted to add a second piece of state that mirrors the first, then delete it and derive it instead.
⚠️ crm-web convention: .claude/rules/react/react-use-effect.md Rule 1 is "Derive state, don't sync it." Code that writes useEffect(() => setX(deriveFromY(y)), [y]) will get flagged in review. Learn the standard pattern here, then internalize that this repo enforces it hard.

📌 7. Refs with useRef

Escape hatches for reaching the DOM and for holding mutable values that don't trigger re-renders.

📖 Referencing Values with Refs · Manipulating the DOM with Refs

  1. Build a "focus the input" button that calls inputRef.current.focus().
  2. Make a "copy to clipboard" button that reads text out of a referenced <pre>.
  3. Use a ref as a mutable flag (e.g. isMountedRef) and observe it changing without causing re-renders.
In crm-web: app/javascript/settings/components/SaveBackupCodes.tsx refs the button/<pre> for clipboard, and an isMountedRef guards against post-unmount state writes. Why: clipboard APIs and async-safety need imperative DOM access that props/state can't express.

⚡ 8. Effects with useEffect

Synchronizing with systems outside React (subscriptions, the DOM, non-React libraries) — and knowing when you don't need an effect.

📖 Synchronizing with Effects · You Might Not Need an Effect · Lifecycle of Reactive Effects

  1. Subscribe to window.resize in an effect and render the current width; return a cleanup function and watch it run.
  2. Use a MutationObserver in an effect to react to a CSS class toggling on <body>; persist the result to localStorage.
  3. Take an effect that only sets state from other state and delete it (reinforces §6).
In crm-web: app/javascript/sidebar/use_more_nav_open_state.ts uses a MutationObserver to sync submenu visibility with sidebar collapse. Why an effect: the sidebar state lives in non-React DOM, so React must subscribe to it externally.
⚠️ crm-web convention: "Never call useEffect directly in components." Use app/javascript/hooks/use_mount_effect.ts (useMountEffect) for run-once-on-mount, or wrap prop-dependent subscriptions in a named custom hook (e.g. useAIMessageSubscription). See .claude/rules/react/react-use-effect.md.

🪝 9. Custom Hooks

Extracting stateful logic into reusable useXxx functions.

📖 Reusing Logic with Custom Hooks

  1. Extract a useLocalStorage(key, initial) hook and use it in two unrelated components.
  2. Write useWindowSize() wrapping the resize logic from §8; reuse it in a couple of places.
  3. Write a useToggle() hook returning [on, toggle, setOn] and refactor your accordion/tabs to use it.
In crm-web: 50+ hooks under app/javascript/hooks/, e.g. use_mount_effect.ts, plus feature hooks like use_more_nav_open_state.ts. Why: custom hooks are the codebase's preferred unit for reusing logic — and the sanctioned wrapper around raw effects (see §8 convention).

🌐 10. Context

Passing data deep through a tree without prop drilling.

📖 Passing Data Deeply with Context · useContext reference

  1. Build a theme context (light/dark) with a provider + a useTheme() consumer hook; toggle it from a deeply nested button.
  2. Make a "current user" context and read it in 3 components at different depths.
  3. Create a context that identifies which "surface" a subtree is in (e.g. "modal" | "page") and have a leaf component render differently per surface.
In crm-web: app/javascript/ai_assistant/hooks/ChatSurfaceContext.tsx marks whether a subtree is the chat panel vs. hub. Why: it lets per-surface Redux slices stay independent without threading a "surface" prop through every component.

🗃️ 11. Reducers & Redux Toolkit

Consolidating complex state transitions into a reducer; then the app-wide version with Redux Toolkit.

📖 Extracting State Logic into a Reducer · Redux Toolkit Quick Start

  1. Rewrite a multi-action to-do list from many useState calls to a single useReducer (add/toggle/delete/edit actions).
  2. Spin up a tiny Redux Toolkit createSlice store for the same to-dos; read with useSelector, write with useDispatch.
  3. Add an async createAsyncThunk that "fetches" items from a mock and handles pending/fulfilled/rejected.
In crm-web: app/javascript/state/tasks_slice.ts manages a normalized TodoMap with thunks and cross-slice updates. Why Redux here: task state is shared app-wide and has many transition types — nested useState wouldn't scale, and slices give predictable, testable updates.

🚀 12. Performance: memo, useMemo, useCallback

Skipping unnecessary recalculation and re-renders — and not reaching for these prematurely.

📖 useMemo · useCallback · memo

  1. Build a list with an expensive derived value; wrap it in useMemo and use React DevTools' Profiler to see the difference.
  2. Pass a handler to a memo()-wrapped child; show it re-rendering, then stabilize the handler with useCallback.
  3. Intentionally over-memoize a trivial component, then reason about when the memo costs more than it saves.
In crm-web: app/javascript/custom_fields/create_form/components/CreateFieldForm.tsx uses useMemo to derive an allowed-document-types list once. Why: the form rebuilds option lists on every render, so memoizing the derivation avoids redundant work on a heavily-interacted form.

📝 13. Forms & Controlled Inputs (react-hook-form)

Controlled vs. uncontrolled inputs, validation, and the library this repo standardizes on.

📖 <input> / controlled inputs · react-hook-form: Get Started

  1. Build a controlled sign-up form (email/password) with inline validation messages using plain useState first.
  2. Rebuild it with react-hook-form's useForm() + register + resolver; compare the boilerplate.
  3. Add a dynamic field array (e.g. "add option" rows for a select field) with useFieldArray.
In crm-web: custom_fields/create_form/components/CreateFieldForm.tsx uses useForm() + FormProvider for a multi-step field builder with dynamic option arrays. Why react-hook-form: complex forms with validation + field arrays are the norm here; the library keeps re-renders down and validation declarative.

🧬 14. Composition, children & Headless Components

Designing flexible components via children and slots instead of rigid props; separating logic from presentation.

📖 Passing JSX as children · (supporting) composition over effects

  1. Build a <Card>{children}</Card> shell, then a <Modal header={...} footer={...}> with named slots.
  2. Write a ConditionalWrapper that optionally wraps its children (e.g. in a link only when an href exists).
  3. Build a headless useDisclosure() hook and render two totally different UIs (dropdown vs. dialog) from the same logic.
In crm-web: components/SidebarBadge.tsx uses a ConditionalWrapper to optionally wrap children in a Popover; the @wds design system is built on headless primitives. Why: headless-first composition keeps logic reusable and lets WDS enforce consistent styling without dictating structure. (See the headless-component-designer skill.)

📡 15. Data Fetching with React Query

Caching, loading/error states, and refetching — replacing ad-hoc fetch + useState + useEffect.

📖 React on data fetching · TanStack Query v4 Quick Start

  1. Fetch from a public API (e.g. GitHub users) with useQuery; render loading, error, and success states.
  2. Add a 5-minute staleTime and a manual refetch button; watch the cache prevent refetching.
  3. Add a useMutation that "creates" something and invalidates the query to refresh the list.
In crm-web: app/javascript/developer_portal/integration-webhooks/hooks/useWebhookEndpoint.ts uses useQuery with a 5-min stale time and per-category error toasts. Why: React Query centralizes caching and request states so feature code stops hand-rolling fetch effects (ties directly back to the §8 "you might not need an effect" rule).

🛡️ 16. Error Boundaries & Suspense

Containing render-time crashes so one broken subtree doesn't take down the page.

📖 Error Boundaries · Suspense

  1. Write a class-based error boundary with a fallback UI; wrap a component that throws on a button click.
  2. Swap to the react-error-boundary library (already a dependency) with a FallbackComponent + reset.
  3. Wrap a lazily-imported component in <Suspense fallback={...}> and watch the fallback appear.
In crm-web: app/javascript/charts/components/ChartFrame.tsx wraps a chart renderer in an error boundary with a fallback. Why: charts are rendered from LLM-produced artifacts that can be malformed, so a boundary keeps a bad chart from crashing the whole AI surface.

🔌 17. Mounting React in Rails & Angular (crm-web integration)

The part no generic React course teaches: how React components actually get onto a page in this monolith. There are 6 patterns — registerComponent is the default.

📖 Read first: .claude/rules/react/react-patterns.md · background: createRoot · createPortal

  1. Read the 6-pattern decision tree, then find one live example of each pattern in the repo (react_blank, registerComponent, react2angular, autoStart.register, programmatic createRoot, createPortal).
  2. Trace one component end-to-end: from a Rails render_component("Name", props: {...}) call → its registerComponent registration in app/javascript/init/ → the rendered React tree (note the Redux/QueryClient providers injected by shared/components/register_component.tsx).
  3. (Reading exercise) Open the wds-new-react-page and wds-registered-screen skills and summarize when you'd pick each.
In crm-web: app/javascript/shared/components/register_component.tsx is the core bridge — it mounts components into data-auto-start divs and wraps them in app-wide providers. Why it matters: picking the wrong mounting pattern causes memory leaks or broken Turbolinks navigation, and (per CLAUDE.md) all new UI must be React — Angular is deprecated and bridged thinly via react2angular.

🧪 18. Testing with React Testing Library

Testing behavior from the user's perspective rather than implementation details.

📖 React Testing Library Intro · Queries & priorities

  1. Write a test for your §5 tabs component: render it, click a tab, assert the right panel shows (userEvent + screen.getByRole).
  2. Test a form's validation: submit empty, assert the error message appears.
  3. Mock a fetch/React Query call and assert the loading → success transition.
In crm-web: spec/javascript/charts/OpportunitiesChart.test.tsx renders the real component, mocks ResizeObserver, fires userEvent, and asserts DOM state. Why this style: CLAUDE.md forbids slow/flaky feature & system specs — frontend behavior is covered by fast component/unit tests like this.

📚 Suggested cadence: §1–§6 in week one (core mental model), §7–§12 in week two (hooks & state at scale), §13–§16 in week three (real feature work), §17–§18 last — they only make sense once the fundamentals are solid, and they're where crm-web diverges most from generic React.
